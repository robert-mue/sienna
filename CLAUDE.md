# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

**sienna** is a **static** jQuery **shell** for single-page apps: a customisable **menu** plus a **workspace** that holds **panels**, where each panel hosts a **content widget** built with the jQuery UI widget factory. Content widgets are loaded dynamically. This repo is the **generic shell** (`src/core/`, `vendor/`, `src/styles.css`) plus a runnable **demo** under `examples/demo/`; real applications live in their own repos and consume this one as a git submodule (the first is `simile`).

There is **no build step, no server, and no npm**. It runs by opening an `index.html` directly (`file://`). Everything is plain classic `<script>` tags — **no ES modules, no imports/exports** — because browsers block ES modules and `fetch`/`import()` over `file://`.

## Repo layout

- `src/core/*.js`, `vendor/*`, `src/styles.css` — **the shell** (the `window.Sienna` framework). This is what other repos consume.
- `examples/demo/` — a **demo app** that consumes the shell: `index.html` (loads the shell via `../../`), `main.js` (bootstrap), `models.js` (a thin model layer), and `widgets/` (five demo content widgets + the manifest). It proves the framework and is the place to exercise shell changes.

## Running

Open `examples/demo/index.html` in a browser (double-click, or `google-chrome examples/demo/index.html`). That's it. Any static file host works too, but none is required.

There are no automated tests/lint/build commands — the tooling was intentionally removed. Verify changes by opening the demo and using it; check the devtools console for errors.

## Key constraints (why it's built this way)

- **Classic scripts only.** No `import`/`export`. Modules communicate through the single global `window.Sienna` (see `src/core/namespace.js`). jQuery is the global `$`/`jQuery` from the vendored scripts.
- **Load order matters.** An app's `index.html` lists scripts in dependency order: vendored jQuery → vendored jQuery UI → `namespace` → `persistence` → `widget-registry` → `user-data` → `actions` → `history` → `files` → `documents` → `panel` → `workspace` → `menu` → `app` → `widget-base` (all shell) → then the app's `widgets/index` → `models` → `main`. Content-widget scripts are **not** listed; they're injected on demand. See `examples/demo/index.html` for the canonical order.
- **Dynamic widget loading = `<script>` injection**, not `import()`. `import()` is blocked over `file://`; injecting a classic `<script>` tag works. This is how the "widgets load dynamically" requirement is met. A widget's `src` in the manifest is resolved relative to the loading `index.html`.
- **Apps consume the shell as a git submodule.** An app repo checks out `sienna/` as a submodule and its `index.html` references `sienna/vendor/…` and `sienna/src/core/…`. Within THIS repo the demo instead reaches the shell via `../../`.

## Architecture

An app's `index.html` loads the scripts, then its `main.js` constructs a `Sienna.App` on `#app` (see `examples/demo/main.js`).

- `vendor/jquery.min.js` — jQuery 3.7 (unchanged upstream).
- `vendor/jquery-ui.js` — a concatenated subset of jQuery UI 1.13 UMD source modules (version, widget factory, mouse, data, disable-selection, plugin, scroll-parent, draggable, resizable) in dependency order. With a global jQuery present, each module's UMD wrapper calls `factory(jQuery)`. Regenerate by concatenating from a jquery-ui source checkout if the subset changes. NOTE: resizable needs handle-placement CSS — shipped in `styles.css`; without it resizing silently no-ops.
- `src/core/namespace.js` — creates `window.Sienna`, and settles the **application id** (`Sienna.appId`, `Sienna.storageKey(slot)`, `Sienna.legacyStorageKey(slot)`) — which must happen here because `persistence` and `userData` name their localStorage keys at load time and `userData` reads its store on the way in. **Every `file://` page shares one origin** (`location.origin` is literally `"file://"`; measured on Chrome 149, for localStorage and IndexedDB alike), so two sienna apps opened from disk would otherwise share `sienna.userData.v1` and silently overwrite each other. The id comes from `window.SIENNA_APP` set by the host page before these scripts, else `?app=` in the query string, else nothing — in which case the legacy un-namespaced keys are used, so an app that has not declared itself keeps working. An app declaring an id for the first time **adopts** its pre-namespacing store once (copied, not moved, so a rollback still finds it).
- `src/core/persistence.js` — `Sienna.persistence`: guarded localStorage access (works on `file://`; keys namespaced per app — see `namespace.js`). Generic slots `readJSON(key)`/`writeJSON(key,value)`/`removeKey(key)` degrade to no-op/null on a disabled/full/corrupt store; the workspace session slot (`save`/`load`/`clear`, key `sienna.workspace.v1`) is a thin wrapper over them.
- `src/core/widget-registry.js` — `Sienna.widgetRegistry`: the single source of truth for which widgets exist. `register(name, { src, label, title, options })` records a widget's script URL and its menu presentation metadata; `loadWidget(name)` injects the `<script>` (once) and resolves to the jQuery UI plugin method name the widget reports via `_loaded(name, method)`. `list()` returns each widget's `{ name, label, title, options }` in registration order — used to build the menu generically.
- `src/core/user-data.js` — `Sienna.userData`: the single global container for all user data, a plain nested object addressed by **path strings** (`'models/graph-2/count'`). App code owns the shape (e.g. a `models` map, a shared `ontology`); the framework only speaks paths. A panel's `ref` is a path into here. Read: `get(ref)` / `has(ref)` / `keys(ref)`. Mutate (the only entry points): `set(ref,value)` (auto-creates intermediate objects, returns prior), `update(ref,patch)` (shallow-merge), `remove(ref)`, `batch(fn)` (one deferred localStorage write). Every mutation **autosaves** the whole store to localStorage (`sienna.userData.v1`, separate from the session slot) and emits `{type,ref,value,prior}` to `subscribe(refPrefix,fn)` listeners (matched when change/watched paths lie on one root-to-node line — the pub/sub substrate). `toJSON(ref)`/`fromJSON(ref,obj)` deep-copy a subtree for file interchange; `load()`/`clear()` manage the persisted slot (values are stored by reference — mutate only via the API, never a `get` result in place).
- `src/core/actions.js` — `Sienna.actions`: the single dispatch point for user actions and the recorder that logs them. `dispatch(action, run?)` records an entry `{ seq, ts, type, target, payload, changes }`; if a `run` effect is given, every `userData` change it causes is captured into `changes` (a "transaction"), so the log audits its own data effects and a later undo layer can reverse them. Captured values are **snapshots** (`Sienna.actions.snapshot`), and are copied again on the way out in `applyChanges` and in `history`: `userData` stores by reference, so a recorded value that was not detached would keep changing after it was recorded — and re-applying one would hand the live store the log's own object. A history has to be immutable both to write and to use. Nested dispatches attribute their changes to the outermost transaction. `subscribe(fn)` observes the stream; `record(on)` toggles recording (effects still run when off — for replay); `log()`/`clear()`/`toJSON()`/`fromJSON(arr)` manage the log. `replay(log?, {speed, onStep})` re-performs a recorded log in order with recording suppressed (so it neither re-logs nor feeds undo); `speed>0` honours the recorded time gaps (video), `0` is instant (testing) and stays in **microtasks** — no timer per entry, so it is unaffected by a background tab clamping `setTimeout` to ~1/sec, which used to make a 54-action replay take the better part of a minute and look hung. Each entry is re-performed by a handler registered via `onReplay(type, fn)` (app registers layout handlers like `panel.add`), or, with no handler, by re-applying its captured `changes` — which via `_watchModel` also re-renders bound widgets, so model edits replay for free. Replay assumes a clean start (clear workspace/userData first) so minted panel ids line up; it does not reconstruct no-per-item actions (Clear workspace) or `panel.ref`. Framework code auto-dispatches what it owns: `menu.js` wraps each selection as `menu.select`; `workspace.js` emits `panel.add`/`panel.close` and, from the panel's classified `onChange`, `panel.move`/`panel.resize`/`panel.minimize`/`panel.maximize`/`panel.ref` — all suppressed during restore (`_suspend`) and `clear()` (`_clearing`). So widget authors get these logged for free.
- `src/core/files.js` — `Sienna.files`: shared file-interchange helpers. `saveAs(filename, obj)` opens a real **Save dialog** via the File System Access API and resolves `{handle, written, cancelled}`; `writeTo(handle, obj)` writes through a handle already granted; `canSaveAs()` feature-detects; `download(filename, obj)` is the Blob fallback (returns whether it started); `pickFile(cb)` is `<input type=file>` → parsed JSON. The **handle** is what makes a real Save possible — the security rule was never "a page may not write files" but "may not write files the user did not choose", and a handle IS that choice, rewritable without re-prompting. Works under `file://` (as webAKT proves), but the API is **Chromium-only**, so callers must cope with getting no handle. Stubbable in tests.
- `src/core/documents.js` — `Sienna.documents`: the shell's **document layer and File menu**. The shell is a host that becomes a particular application, and the conventional furniture along the top should not vary with which one — so **File is the shell's**, not the app's. Generic: documents live at `<root>/<id>` in `userData`, `list()`/`create()`/`import(obj)`/`save(path)`/`saveAs(path)`/`hasFile(path)`/`open(app, path)`, saved as JSON via `Sienna.files`, each write dispatched so it is undoable. **`saveAs` remembers the file** the user picked (a handle, kept in memory keyed by document path, not persisted) so **`save` writes straight back to it** — a real Save. Where the File System Access API is absent both degrade to a download and Save means Save as; both are listed everywhere regardless, a menu that changes shape between browsers being harder to describe than a command that quietly does less. A lapsed grant re-prompts rather than reporting a failure the user cannot act on. `menuItems(app)` builds New / Open file / Save / Save as file / one entry per stored document, and reports a refused save instead of swallowing it. Only two things cannot be generic and so are registered via `configure({ root, label, widget, create, validate })`: **what an empty document looks like** and **which widget opens one** — the shell never inspects a document's contents, keeping the app sole authority over its own shape (the same boundary `userData` draws). `App.setMenu` prepends this File menu automatically and refreshes it when the SET of documents changes; an app that never calls `configure()` gets no File menu. NOTE: `examples/demo/models.js` predates this and still builds its own File menu from `Sienna.models` — a candidate to migrate onto `documents`.
- `src/core/history.js` — `Sienna.history`: unlimited undo/redo riding the action stream. Subscribes to `actions`; each dispatched entry carrying userData `changes` becomes one undoable transaction (scope = **userData only**, so layout actions like panel move/resize aren't undone; a new action clears redo). `undo()`/`redo()` re-apply the captured before/after values straight to userData (remove when a value was absent) WITHOUT dispatching — so the log isn't polluted — but they emit userData events, so `_watchModel`-ing widgets re-render and the change is visible. `canUndo`/`canRedo`/`depth`/`clear`; `scope` is the seam for undoing layout later. `main.js` adds an Edit menu (Undo/Redo) and Ctrl/Cmd-Z / Ctrl/Cmd-Shift-Z (Ctrl-Y) shortcuts (suppressed while typing in a field).
- `src/core/app.js` — `Sienna.App` composes menu + workspace into the root; `setMenu`, `addPanel`, `clearWorkspace`, `restore`. Persists on every workspace change.
- `src/core/menu.js` — `sienna.menu` widget. Config-driven `items` array of `{ label, onSelect?, items? }` (nested `items` = submenu).
- `src/core/workspace.js` — `sienna.workspace` widget. `addPanel({ title, widget, options, ref, id, geometry, minimized, maximized })`; mints a stable panel `id` (`'p0'`, `'p1'`, … via `_mintId`) when one isn't supplied, seeding the counter past restored ids so new panels never collide. Keeps a metadata entry per panel so `serialize()`/`restore()` round-trip the whole workspace (including each panel's `id` and `ref`); `panelById(id)` looks one up (used by replay). Fires `onChange` on any add/remove/move/resize/min/maximise (suspended during `restore`).
- `src/core/panel.js` — `sienna.panel` widget = titlebar (title + minimise/maximise/close) + content div. `panel('content')` returns the content element. Draggable by titlebar and resizable; `minimize`/`maximize` toggles; tracks its "normal" `geometry()` for restore/persist. Absolutely positioned; reports `onFocus` (raise) and `onChange` (persist). Button glyphs are pure CSS. Also carries two identifiers, both persisted: `id` — a stable per-instance id (e.g. `'p3'`, usually assigned by the workspace), via `panel('id')`; and `ref` — a path string addressing the "thing" the panel is a view of (e.g. `'models/graph-2'`), keyed into `Sienna.userData`, via `panel('ref')` get / `panel('ref', str)` set. The panel doesn't interpret `ref` — it's groundwork for a future pub/sub layer that will scope cross-panel updates to panels sharing a subject. `id` names the panel; `ref` names what it views (several panels may share one `ref`).
- `examples/demo/widgets/index.js` — the widget **manifest**: the one place listing the app's content widgets (script URL + label/title/options). `main.js` builds the Widgets menu from `widgetRegistry.list()`, so `main.js` has no per-widget knowledge — adding a widget is a single registration here.
- `examples/demo/widgets/*.js` — content widgets: `clock`, `hello`, `counter`, `notepad`, `colorpicker`. `counter` is the pilot for the model-binding contract (it extends `$.sienna.widgetBase`): bound (panel has a `ref`) its count lives in the model at `<ref>/count` and it `_watchModel`s to re-render on model changes (sibling views + undo update live); unbound (Widgets menu) it keeps a local count via `state()`.
- `src/core/widget-base.js` — `$.sienna.widgetBase`: optional base a content widget extends (`$.widget('sienna.x', $.sienna.widgetBase, {…})`) for model binding scoped to its host panel's `ref`. Gives `_ref()`/`_bound()`/`_model()`/`_get(sub)`/`_set(sub,v)` (no-ops when unbound) and `_action(name, payload, run)` — dispatch a logged `'<widget>.<name>'` action targeting the panel, with `run`'s userData changes captured. For live updates a widget opts in with `_watchModel(handler)` in `_create`: `handler` runs on any userData change at/under the panel's `ref`, so **sibling panels sharing a `ref` stay in sync and undo/import show visibly** (this is the pub/sub layer). The subscription auto-detaches when the widget's element leaves the document, so no teardown is needed.
- `examples/demo/models.js` — `Sienna.models`: the app's thin **model layer** over `userData` — the one place that knows user data is a `models/<id>` map (`{ id, name, … }`). `list()` / `get(ref)` / `ref(id)`; lifecycle `create` / `copy` (Save As) / `rename` / `remove`; a *current* model (`current`/`setCurrent`); file interchange `exportFile`/`importFile`/`exportAll`/`importAll` (via the shared `Sienna.files` helpers — file:// forbids silent writes). localStorage is the live autosaved store (via `userData`), so there is no "Save". `main.js` builds a **File menu** from this; `File ▸ New` and `File ▸ Open` open a panel viewing the model (the `counter` pilot, `ref` → the model path). The `File ▸ Open` submenu rebuilds only when the *set* of models (ids/names) changes — a `userData.subscribe('models', …)` guarded by a signature check, so a bound counter's count changing doesn't rebuild the menu.

### Content widget contract

A content widget script must (1) register itself via `$.widget('sienna.<name>', {...})` using the global `$`, and (2) at the end call `window.Sienna.widgetRegistry._loaded('<name>', '<name>')` where the second arg is the jQuery UI plugin method name to invoke on the panel's content element. Add it to the manifest in `examples/demo/widgets/index.js` via `register('<name>', { src, label, title, options })`; the menu picks it up automatically.

A widget that holds **shared user data** SHOULD extend `$.sienna.widgetBase` (see above) and keep that data in its model via `_set`/`_get`, wrapping user actions in `_action` — then logging, capture, and (later) undo work with no widget-specific code. That's the whole extra contract.

For persistence, a widget MAY implement a `state()` method returning a plain, JSON-serialisable object — now for **view state** only (selection, scroll, or a widget's *unbound* fallback data). On save it's merged into the panel's stored `options`; on restore the merged options are passed back to the widget's constructor, so `state()` keys must be constructor option names (e.g. unbound counter returns `{ start }`, notepad returns `{ text }`). Shared data belongs in the model (userData), which persists on its own; a bound widget's `state()` is typically empty. Widgets without `state()` restore from their original options.

### Conventions

- The `.menu()` / `.workspace()` / `.panel()` plugin names are safe because `vendor/jquery-ui.js` includes only the widget factory + draggable/resizable, not jQuery UI's own `menu` widget. If you add more of jQuery UI to the vendor bundle, check for name collisions.
